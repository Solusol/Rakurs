# Local project attachment manifests: development module

No existing application file is changed by this stage. The module is not imported by index.html, app.js or cloud.js. No user data is read or rewritten merely by adding these files. No migration, deployment, resource creation, deletion or quota release occurs.

createAttachmentEditor accepts a getReadyMetadata callback and defaults to readProject/saveProject from local-projects.mjs. replace({account, project, expectedRevision, fileIds}) requires an existing account-scoped IndexedDB project and its exact revision. It snapshots the project, verifies each requested file's ready state, owner, project, ID, byte count and SHA-256, then saves through the existing revision-checked transaction. A conflicting save during metadata lookup must abort instead of overwriting another tab. Storage errors, including the existing adapter's RevisionConflictError, propagate to the caller.

The reserved _rkAttachments field has version:1, ownerId, projectId and files:[{id,bytes,sha256}]. All other project fields, including inline media, unknown fields and updated, are preserved. This module deliberately does NOT update the legacy cloud timestamp: it writes only the new local IndexedDB revision. Cloud publication needs a separately coordinated versioning step. Unknown manifest versions/owners/projects or extra top-level manifest fields are rejected rather than overwritten. replace is full-list replacement, with at most 100 unique file UUIDs; passing [] removes only local references. It does not remove R2 objects or release their reservations.

The manifest is a local display/reference index, not an authorization token or authoritative reference count. Caller must derive account from the signed-in session and implement authenticated metadata lookup; no browser-to-Durable-Object bridge is supplied. Reads must continue to use server-side Auth/project/ready checks. Metadata lookup and local save are not a cross-service atomic transaction: later revocation or server deletion must be handled by the future lifecycle protocol. Never run cleanup based only on a missing local reference.

Current production synchronization still serializes legacy localStorage project JSON. The new IndexedDB path has no application migration or UI hooks. Importing this module alone does not integrate remote attachments or make them visible. Before activation: browser IndexedDB tests, preview/reference handling, copy/import/export behavior, preservation across every save path, safe cloud conflict handling, server lifecycle and end-to-end authorization are required.

Run: node --test storage/project-attachments.test.mjs
Twelve unit tests passed with injected in-memory read/save and metadata functions. These test the editor contract, not browser IndexedDB, actual multi-tab scheduling, Supabase or Cloudflare. During this local unit run the unused default IndexedDB imports were stubbed to throw if called. No new claim of deployed persistence or migration coverage is made.
